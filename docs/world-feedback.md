# World ID feedback from building vet402

I am the builder of vet402, and I used World ID 4.0 session proofs of Proof of Human (`@worldcoin/idkit-core` 4.6.0) to make a person approve every budget and every hold before money reaches an AI agent's wallet, on staging from 2026-10-28 and in production with World App on iOS on 2026-11-05. On 2026-11-06 I made the check grow with the amount: a hold above 0.5 USDC also asks for a selfie check in the same approval, so a large hold needs the person at the phone as well as a unique human. This is the integration debrief: time to first success, what worked well, what would make it even better, and the one improvement with the greatest impact.

## What worked well

- **Time to first success was about 25 minutes.** Going from handing over the instruction to "Budget set." on staging took from 16:05 to 16:29 UTC on 2026-11-05.
- **Production worked with the staging signer.** On 2026-11-05 at 22:16 UTC, with `WORLD_ENVIRONMENT=production`, the same app id, rp id and signer key, my Orb verified World App on iOS returned "Budget set." and then "Held 1 USDC for this job." The verified result reads environment production, protocol 4.0, proof_of_human. The same key and registration served both.
- **Session proofs fit a budget.** The first budget is a createSession, and every hold is a proveSession of that same session with the signal `<hold id>:<amount>`. Only the person who set the budget can approve a hold, and a proof made for another hold is refused by the signal check with "Not approved: this approval is for another hold."
- **Credentials compose in one approval.** IDKit 4.6.0 accepts `all(CredentialRequest('proof_of_human', { signal }), CredentialRequest('selfie', { signal }))` on `proveSession`, which I checked on 2026-11-06 by building the request locally with the bridge call stubbed. A large hold stays one QR code, and the result carries one proof per credential, each with its own `signal_hash` and session nullifier, so the backend checks both.
- **The verify endpoint says what it checked.** `POST https://developer.world.org/api/v4/verify/{rp_id}` returns the environment, so the backend can refuse a staging proof in production.

## What would make it even better

1. **A link to the right team when the Developer Portal opens an empty one.** On 2026-11-05, shortly before the 22:16 UTC production run, I signed in to developer.world.org with World App to check the Signer address. The portal showed a team named "Anonymous user" with "Welcome to World ID" and "Create new app", and none of my apps. Signing out and back in with my email account showed vet402's app. A line on the empty screen saying another team exists for this person, with a link to switch, would take a builder straight to the app.
2. **A name such as "World App listing" for "Verification" in the left menu.** In the same session, on 2026-11-05 shortly before 22:16 UTC, I opened "Verification" while looking for the World ID settings. It led through "Basic information", "Availability", "Localized content" and "Review", which is the request to list an app in World App. A distinct name would keep it apart from World ID.
3. **The Simulator's Cancel sent back to the app.** First seen on staging by 2026-10-28 21:00 UTC, and the reason the app has its own Cancel request. After pressing Cancel in the World ID Simulator, the page kept waiting until the app's own 2 minute limit closed it with "Not approved. Nothing was held or paid." Sending the cancel back as a `user_rejected` result, an error code IDKit 4.6.0 already lists, would let a tester see the cancel path as it is.
4. **A confirmation screen that waits for Continue.** On 2026-11-05 between 16:05 and 16:29 UTC, pasting the request URL into the Simulator opened the confirmation screen at once. One extra press closed it, and the request was used up. The "Continue" button on that screen also sits partly below the bottom edge. Waiting for the press, and keeping the button inside the screen, would make each try count.
5. **Selfie Check on staging, or one line saying it is production only.** On 2026-10-28 (UTC) Selfie Check returned `credential_unavailable` on staging for both `request` and `createSession`, and `proof_of_human` passed there. The Simulator's screen reads "Unique device" while the returned identifier is `proof_of_human`. Matching the Simulator's label to the identifier would help too.
6. **One line on reading `results` when a request asks for two credentials.** On 2026-11-06, while adding the selfie check for large holds, I read the OpenAPI for `POST /api/v4/verify/{rp_id}`. Its 200 answer is described as "At least one proof verified successfully", and each proof gets its own line in `results`. So a hold that asks for Proof of Human and a selfie check could read `success: true` with only Proof of Human passing. vet402 now holds only when `results` lists `selfie` with `success: true` and no line failed. A sentence in the session proofs guide, next to the selfie example, saying to check each identifier in `results` would lead every builder to the same check.
7. **An example of a signal on a session proof in the README.** On 2026-11-06 around 01:06 UTC (commit `bd05f86`) I bound a budget's amount to its first proof. The `@worldcoin/idkit-core` 4.6.0 README shows `createSession` as `.constraints(IDKit.CredentialRequest("proof_of_human"))`, and shows a signal on presets such as `orbLegacy({ signal: "user-123" })`. I found in `dist/index.d.ts` that `CredentialRequestType` has `signal?: string | Uint8Array`, so `CredentialRequest("proof_of_human", { signal })` works in `createSession` and `proveSession`, and the backend tests check the `signal_hash` against it. One example with a signal under session proofs would answer it right away.

8. **A sheet or a `credential_unavailable` answer for a Proof of Human and selfie request in production.** On 2026-11-06 at 05:05 and 05:06 UTC, in production with World App on iOS, a budget and a 0.5 USDC hold were approved in the same session ("Held 0.5 USDC for your agent."). Between 05:09 and 05:11 UTC a 1 USDC hold asked for `proof_of_human` and `selfie` together, with `all()` on `proveSession`. Scanning the QR code opened World App, which went to its home screen with no approval sheet, twice. The app received no answer, and the request closed at its own 2 minute limit. vet402 already shows "Not approved: this hold needs a selfie check, which World App could not give right now. Nothing was held." when `credential_unavailable` comes back. A sheet that explains what is needed, or that answer sent back to the app, would let every builder show the person why.

## The one change with the biggest effect

Send the Simulator's Cancel back to the app. It is the one alternative path every World ID integration shows, and with it staging would test that path with no extra code in the app.
