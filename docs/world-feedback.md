# World ID feedback from building vet402

I am the builder of vet402, and I used World ID 4.0 session proofs of Proof of Human (`@worldcoin/idkit-core` 4.6.0) to make a person approve every budget and every hold before money reaches an AI agent's wallet, on staging from 2026-10-28 and in production with World App on iOS on 2026-11-05. This is the integration debrief: time to first success, friction, missing capability or documentation, and the one improvement with the greatest impact.

## What worked well

- **Time to first success was about 25 minutes.** Going from handing over the instruction to "Budget set." on staging took from 16:05 to 16:29 UTC on 2026-11-05.
- **Production worked with the staging signer.** On 2026-11-05 at 22:16 UTC, with `WORLD_ENVIRONMENT=production`, the same app id, rp id and signer key, my Orb verified World App on iOS returned "Budget set." and then "Held 1 USDC for this job." The verified result reads environment production, protocol 4.0, proof_of_human. I did not have to rotate a key or register anything new.
- **Session proofs fit a budget.** The first budget is a createSession, and every hold is a proveSession of that same session with the signal `<hold id>:<amount>`. Only the person who set the budget can approve a hold, and a proof made for another hold is refused by the signal check with "Not approved: this approval is for another hold."
- **The verify endpoint says what it checked.** `POST https://developer.world.org/api/v4/verify/{rp_id}` returns the environment, so the backend can refuse a staging proof in production.

## Where I lost time

1. **Signing in to the Developer Portal with World App opened a different, empty team.** On 2026-11-05, shortly before the 22:16 UTC production run, I signed in to developer.world.org with World App to check the Signer address. The portal showed a team named "Anonymous user" with "Welcome to World ID" and "Create new app", and none of my apps. Signing out and back in with my email account showed vet402's app. For a moment it looked as if the app was gone, and the screen invited me to create a new one. A line on the empty screen saying another team exists for this person, with a link to switch, would prevent that.
2. **"Verification" in the left menu is the World App listing, not World ID.** In the same session, on 2026-11-05 shortly before 22:16 UTC, I opened "Verification" while looking for the World ID settings. It led through "Basic information", "Availability", "Localized content" and "Review", which is the request to list an app in World App. A name such as "World App listing" would keep it apart from World ID.
3. **The Simulator's Cancel does not reach the app.** First seen on staging by 2026-10-28 21:00 UTC, and the reason the app has its own Cancel request. After pressing Cancel in the World ID Simulator, nothing came back to the page. The request stayed waiting until the app's own 2 minute limit closed it with "Not approved. Nothing was held or paid." A tester cannot see the cancel path without a second button in the app. Sending the cancel back as a `user_rejected` result, an error code IDKit 4.6.0 already lists, would make the path testable as it is.
4. **The Simulator's confirmation screen is easy to close by mistake.** On 2026-11-05 between 16:05 and 16:29 UTC, pasting the request URL into the Simulator opened the confirmation screen without a press on "Continue". One extra press closed it, and the request was used up. The "Continue" button on that screen is also cut off at the bottom. Waiting for the press, and keeping the button inside the screen, would remove both.
5. **Selfie Check is not available on staging.** On 2026-10-28 (UTC) Selfie Check returned `credential_unavailable` on staging for both `request` and `createSession`. Only `proof_of_human` passes there. The Simulator's screen reads "Unique device" while the returned identifier is `proof_of_human`. Either Selfie Check on staging, or one line in the docs that it is production only, would save the try. Matching the Simulator's label to the identifier would help too.
6. **The README does not show a signal on a session proof.** On 2026-11-06 around 01:06 UTC (commit `bd05f86`) I bound a budget's amount to its first proof. The `@worldcoin/idkit-core` 4.6.0 README shows `createSession` only as `.constraints(IDKit.CredentialRequest("proof_of_human"))`, and shows a signal only on presets such as `orbLegacy({ signal: "user-123" })`. I found in `dist/index.d.ts` that `CredentialRequestType` has `signal?: string | Uint8Array`, so `CredentialRequest("proof_of_human", { signal })` works in `createSession` and `proveSession`, and the backend tests check the `signal_hash` against it. One example with a signal under session proofs would answer it.

## The one change with the biggest effect

Send the Simulator's Cancel back to the app. It is the one alternative path every World ID integration has to show, and today it cannot be tested on staging without extra code in the app.
