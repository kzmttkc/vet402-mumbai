# Arc Studio feedback from building vet402 on Arc

I am the builder of vet402, and I used Arc Studio from the CLI (`@circle-fin/arc-studio-cli` 1.2.1, driven by Claude Code) and from the Studio web workspace to build the SealedDelivery contract and its app at ETHGlobal Mumbai, between 2026-11-05 15:30 UTC and 2026-11-06 01:55 UTC. The Arc Studio team asked for feedback at the Mumbai workshop, so each suggestion below gives the command or screen, what came back, and the change that would make Studio even better.

## What worked well

- **The smart contract review caught real bugs.** On the first draft of SealedDelivery it reported a High: a Promise has to name the buyer, or it could be copied from a pending claim. On the next draft it reported nonce squatting, where a stranger could claim a nonce first and lock the real buyer out. Both were real, and both are fixed in this repo.
- **The Contracts panel.** Every deployment (5 of SealedDelivery by 2026-11-05 23:20 UTC, as `arc-studio deployments -s mumbai` lists them), the 28 functions and the contract state sit in one place, and the latest deployment is easy to tell apart.
- **Starting from a plain prompt.** P1 (phone app with a buyer key and a hold key) came back in about two minutes with the backend, the keys and a working screen.
- **The web code editor kept working at the usage limit.** On 2026-11-06 around 01:25 UTC, with the CLI at 100% of its limit, I pasted the final `SealedDelivery.sol` into the Studio code editor and it showed "Auto saved". `arc-studio cat` then read back a file whose sha256 starts with `93a08889572a08f3`, the same as my local copy.
- **The Studio Terminal ran everything.** In that same session the Terminal ran `forge test` on the final contract with 246 tests passed and 0 failed, and `bash scripts/test.sh` on the whole app with 432 passed and 0 failed.
- **Tracing picked up Arkiv's JSON-RPC.** On 2026-11-06 at 02:06 UTC, once it was on, Tracing listed the page's `arkiv_query` calls to Rabdi next to its own API calls, with no setup for Arkiv.
- **Reads still work at the limit.** On 2026-11-06 at 02:04 UTC `arc-studio usage --json` returned `"percentUsed":100`, and `arc-studio deployments`, `ls` and `cat` all still answered.

## What would make it even better

1. **A time next to `percentUsed`.** The usage limit is a rolling 24 hour window. On 2026-11-05 between 15:30 and 21:25 UTC, `arc-studio usage --json` returned `{"percentUsed":90,"windowMs":86400000}` after about twelve turns. Showing when the next 10% frees up would let a builder plan the last sync.
2. **File transfer that is not an agent turn.** On 2026-11-06 around 01:20 UTC, at 100% of the limit, I ran `arc-studio run --file` to send the final contract. It answered "Get a usage limit increase for your organization:" followed by `arc-studio upgrade`, and the file in the sandbox stayed as it was. A few minutes later the web code editor saved the same file with no trouble. Letting the CLI copy files at the limit too would keep the CLI and the editor in step.
3. **The allowed destinations named in the `--file` error.** On 2026-11-05 between 15:30 and 21:25 UTC, `arc-studio run --file x.json:context/x.json` was refused with a destination error. Sending it as a plain `--file` put it under `context/`, and the agent reported that `context/` was out of its reach, so it re-created the fixture by hand. An error that lists the allowed destinations would make the first try the right one.
4. **`pull --changed` that falls back to the last turn with files.** On 2026-11-05 between 15:30 and 21:25 UTC, after a turn that wrote no files, it answered "this session's last turn recorded no file changes". Pulling by `--paths` worked. When `pull` skips files to protect local edits, it says how many. Falling back to the last turn that changed files, and listing the skipped paths, would make both cases one command.
5. **A delete option on `run --file`, or a sync that mirrors removals.** After I deleted four test files locally, the sandbox kept them. On 2026-11-05 between 22:10 and 22:20 UTC, in the turn before the final deploy, Studio's `forge test` counted 224 tests while my checkout had 219. Mirroring removals would keep the counts equal.
6. **A notice when an upload removes a template script.** The Studio template's `package.json` had `"deploy:self": "bun run ./scripts/self-deploy.ts"`, and that script reads `CIRCLE_API_KEY`, `CIRCLE_ENTITY_SECRET` and the other `CIRCLE_*` keys. I removed the template scripts from my copy on 2026-11-05 at 18:29 UTC (commit `341edd6`) and later sent it with `arc-studio run --file`. On 2026-11-06 at 02:04 UTC, `arc-studio cat -s mumbai package.json` showed no `deploy:self` in the sandbox. A line listing the template scripts an upload removes would make that visible at once.
7. **Studio's deploy from the Terminal, or a way to add an address to Deployments.** On 2026-11-06 around 01:35 UTC I deployed the final contract from the Terminal. The `CIRCLE_*` keys that the template's deploy script needs come with an agent turn, so from the Terminal I used `forge create` with my own testnet key. The receipt of transaction `0x38095fb7894b86e2c57be1d1bb6e367ddbc6fd9fc9276ecacc43ac37701b3733` reads status `0x1` and contract `0xe9c35ad2caf5d76ca5a5f61ca2256995197c2a4b`, in block 70951830 at 01:35:22 UTC. On 2026-11-06 at 02:04 UTC, `arc-studio deployments -s mumbai` listed the five earlier addresses, ending with `0x2750c52890c4b90394a984242650e3e8eb8cae6f`. A Terminal command for Studio's deploy, or a way to add an existing address to Deployments, would keep the panel complete.
8. **A Deploy button next to the Deployments list.** On 2026-11-06 between 01:20 and 01:55 UTC the Contracts panel showed the Deployments list, and the Deploy button appears while the list is empty. Keeping the button next to the list would allow a new version within the same app.
9. **The forge and solc versions next to the test count, and a list of the tests that ran.** `test_Gas_PerKbSlope` compares gas per KB at two sizes. In Studio its slopes came out 12% apart while they were 1% apart locally, so I loosened it to a bound of twice (commit `b7edde7`). On 2026-11-05 between 22:10 and 22:20 UTC, Studio reported `105191 >= 92406` for it while all 219 passed locally, and on 2026-11-06 before 01:31 UTC the Studio Terminal reported `105217 >= 92432`. The sandbox runs forge 1.7.1 and my machine runs 1.8.3. The gap sat in the first, cold call: one warm up call before measuring (commit `5717ae7`) made it pass in both, with 246 passed in Studio. Studio's Terminal reported 246 tests passed, and my checkout of `4ad89eb` reported "236 tests passed, 0 failed, 0 skipped (236 total tests)" in 19 suites on 2026-11-06 at 02:12 UTC. Both hold the same 19 test files with the same number of test functions, and the sandbox's `contracts/test-integration` holds only `.gitkeep`. Printing the versions next to the count, and listing the tests that ran, would show where the other 10 come from.
10. **A restart button on the Preview.** On 2026-11-06 between 01:20 and 01:55 UTC, after I sent other files into the sandbox, the vite server that Studio had started for the Preview answered "Forbidden". Restarting the server from the Terminal fixed it. A restart button, or a restart when its config file changes, would make that one click.
11. **Tracing that starts on the first load.** On 2026-11-05 my app ran outside the Preview, so Tracing said "No trace events yet" while the deployment then in use had 71 transactions on Arc testnet (read 2026-11-05 21:30 UTC). On 2026-11-06 between 01:50 and 01:59 UTC I ran a dispute from the public page inside the Preview, served as a production build (`vite build`), and Tracing read "No trace events yet. Interact with the preview to see trace events." The template's `src/tracing.ts` runs when `import.meta.env.DEV` is true, so a build sends no events. On 2026-11-06 at 02:06 UTC I started the same page in the sandbox with the dev server (`VITE_PUBLIC_PREVIEW=1`, loading `src/tracing.ts` first). After the Preview loaded, Tracing read "No trace events yet" until I switched its toggle off and on once. Then it listed `GET /api/receipts`, `/static/*.json`, `/v1/x402/transfers` and `arkiv_query`. `tracing.ts` starts with `_enabled = false` and turns on when the parent frame sends a `studio-trace-config` message, so an app that loads it late misses the one sent when the Preview loads. Sending `studio-trace-config` again on every load of the Preview iframe, or having `tracing.ts` start enabled or ask the parent for the state at start, would make it work on the first load. A line in the panel saying a production build sends no events would explain the empty case.
12. **Arc testnet in `getSupported()` and a published `eth_getLogs` limit.** On 2026-11-05 before 21:25 UTC, `BatchFacilitatorClient.getSupported()` returned no Arc testnet entry, so the seller builds its payment terms from constants. During the demo runs the public node `rpc.testnet.arc.io` answered `eth_getLogs` with "rate limit exceeded", so the app falls back to `rpc.testnet.arc.network` and `arc-testnet.drpc.org`. Both additions would let an app drop those workarounds.

## The one change with the biggest effect

Let the CLI send and remove files without an agent turn, as the web code editor already saves at 100%. Items 2, 5 and 6 come from the same place, and at the end of the event the editor is what carried my final contract into Studio.
